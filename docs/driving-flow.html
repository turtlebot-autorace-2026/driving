DRIVING · CODE WALKTHROUGH

영상 한 장이
주행 명령이 되기까지

공통 노드는 영상을 받고, 선택된 검출기와 조향기를 호출한다. 계산이 끝나면 그 결과가 아직 유효한지 확인한 뒤 속도와 디버깅 영상을 발행한다.

2026-11-03 코드 기준 · ROS 2 Galactic / Python 3.8 대상 · 브라우저에서 여는 독립 문서

전체 흐름FrameJob과 FrameResult한 프레임 따라가기상황별 단계 보기선택과 파라미터토픽과 basic코드 읽는 순서

1. ROS 콜백과 영상 계산의 역할

노드는 차선 좌표나 미검출의 뜻을 해석하지 않는다. 그 의미는 선택한 검출기와 조향기가 합의한다. 노드가 확인하는 최종 출력은 유한한 수로 구성된 Twist다.

2. FrameJob은 작업 추적, FrameResult는 계산 결과

둘 다 @dataclass로 만든 작은 Python 자료 묶음이다. 필요한 필드를 받는 생성자가 자동으로 만들어진다. ROS 토픽에 이 객체 자체를 발행하지는 않는다.

노드가 보관

FrameJob

“어느 설정으로, 언제 받은 영상을 처리하고 있으며, 끝났는가?”를 확인하는 정보다.

FrameJob(
    generation=3,
    received_at=100.0,
    future=처리_작업의_Future,
)

작업 자체를 실행하는 클래스는 아니다. 실행은 ThreadPoolExecutor에 맡긴다.

worker가 반환

FrameResult

“이 영상으로 계산한 속도는 무엇이며, 함께 보낼 디버깅 영상이 있는가?”를 담는다.

FrameResult(
    twist=계산한_Twist,
    debug_image=JPEG_메시지_또는_None,
    debug_error=경고_문구_또는_None,
)

중간 검출값인 center나 경로는 여기에 보관하지 않는다. 그 값은 detect → compute 사이에서 전달된다.

필드실제 의미확인하는 이유
FrameJob.generation작업을 시작할 때의 선택·설정 번호현재 번호와 다르면 예전 알고리즘/파라미터의 결과다. 영상마다 증가하는 번호는 아니다.
FrameJob.received_at활성 영상 콜백에서 기록한 monotonic() 시각현재 시각과 비교해 0.5초보다 오래된 결과인지 확인한다. 촬영 시각 header.stamp와 다르다.
FrameJob.futureworker에 맡긴 작업의 완료 상태와 반환값/예외에 접근하는 객체done()으로 완료를 확인하고, result()로 결과를 꺼낸다.
FrameResult.twist조향기가 만든 geometry_msgs/Twist검사를 통과하면 cmd_vel로 발행한다.
FrameResult.debug_image선택적인 CompressedImageNone이면 해당 프레임의 디버깅 발행을 생략한다.
FrameResult.debug_error디버깅 생성 과정에서 발생한 오류의 문자열경고를 기록하면서 정상 조향값을 유지한다.

두 객체를 이어 주는 Future

# worker에 맡기면, 계산 완료를 기다리지 않고 Future를 받는다.
future = worker.submit(_run_algorithms, detector, controller, msg)
job = FrameJob(generation, received_at, future)

# 이후 감시 콜백에서 완료 및 유효성을 확인한다.
if job.future.done():
    # 실제 코드는 generation과 입력 나이도 먼저 검사한다.
    frame = job.future.result()  # 정상 완료라면 FrameResult
    cmd_vel_pub.publish(frame.twist)

위 코드는 관계를 설명하는 축약 예시다. 실제 코드에는 예외 처리와 디버깅 발행도 있다. Future.result()는 미완료 상태에서 호출하면 기다리지만, 현재 노드는 done()을 먼저 확인한다. 계산 중 예외가 발생했다면 result()에서 그 예외가 다시 발생한다.

3. 한 프레임을 순서대로 따라가기

  1. 노드를 시작한다 — main → __init__

    ROS 초기화 후 두 분모 파라미터를 선언·검사한다. 등록표에서 기본 basic_sat / basic_p 객체를 만들고, publisher·subscription·worker·감시 타이머를 준비한다. rclpy.spin()이 ROS 콜백을 실행한다.

  2. 입력 영상을 고른다 — camera_callback → process_frame

    세 카메라 토픽의 마지막 메시지를 각각 보관한다. 계산은 활성 검출기의 input_topic에 해당하는 입력만 진행한다. 확정된 파라미터 변경을 먼저 반영하고 (수신 시각, msg)를 대기 슬롯에 넣는다.

  3. 한 작업을 제출한다 — _start_next_frame

    기존 _job이 없고 대기 영상이 있을 때만 시작한다. 대기 중 이미 0.5초보다 오래된 영상은 버린다. submit()으로 받은 Future와 설정 번호·수신 시각을 FrameJob으로 묶어 보관한다.

  4. 알고리즘을 실행한다 — _run_algorithms

    검출기가 압축 해제·전처리·차선 검출을 한다. 조향기가 결과를 받아 Twist를 만든다. Twist 타입과 여섯 성분의 유한성을 검사하고, get_debug_image()가 있으면 호출한다. 결과를 FrameResult로 반환한다.

  5. 회수하고 발행한다 — _poll_pipeline

    0.05초 주기로 완료 여부를 확인한다. 완료된 작업을 로컬 변수로 옮기고 _job=None으로 만든다. 설정 번호가 같고 입력 나이가 0.5초 이내인 결과만 꺼내 발행한다. 마지막에 최신 대기 영상의 처리를 시작한다.

  6. 유효한 입력이 끊기면 정지한다

    _last_valid_frame_at은 마지막 유효 결과를 만든 영상의 수신 시각이다. 아직 유효 결과가 없거나 그 시각부터 0.5초를 초과하면 0 Twist를 발행한다. worker가 계산 중이어도 감시 콜백이 실행되면 이 확인은 계속한다.

0.5초에는 대기 시간 + 검출·조향 + JPEG 생성 + 완료 후 감시 콜백까지의 대기가 포함된다. 0.05초 타이머는 결과를 확인하는 주기이며, 카메라 FPS나 항상 일정한 제어 주기를 보장하지 않는다.

4. 상태가 바뀌는 모습을 단계별로 보기

버튼으로 시점을 이동하며 _job, _pending_frame, 계산 결과를 비교해 보자. 시각은 설명용 상대 시간이며 실제 ROS 실행이나 실시간 측정은 아니다.

A·B·C는 서로 다른 입력 영상이다. Future에 결과가 준비되어 있어도 노드의 유효성 검사를 통과해야 발행된다.




정상 처리: 영상 A 수신 → FrameJob 생성 → worker가 FrameResult 반환 → 감시 콜백이 회수·검사 → Twist/JPEG 발행.
처리 중 B 다음에 C가 들어오면 대기 영상은 C로 교체된다. 설정이 바뀌면 이전 FrameJob은 끝날 때까지 남지만 그 결과는 버린다. 0.5초를 초과한 결과도 버리며, 디버깅만 실패하면 유효한 Twist는 발행한다.







5. 알고리즘 선택과 파라미터 변경




String 선택 토픽
다른 알고리즘으로 바꿀 때
  1. 문자열의 앞뒤 공백을 제거한다.
  2. 같은 조합이면 그대로 둔다.
  3. 등록된 이름으로 두 객체를 새로 생성하고 설정을 적용한다.
  4. 성공하면 이름과 객체를 교체한다.
  5. _reset_processing() 후 세 카메라 캐시를 비운다.
등록되지 않은 이름·생성 실패·지원하지 않는 입력 토픽은 기존 선택을 유지한다. 한쪽만 바꾸어도 두 객체를 다시 만든다.


ROS 파라미터 서비스
분모 값을 조절할 때
  1. _validate_parameters()에서 양수인 유한 실수인지 검사한다.
  2. ROS가 변경을 확정해 저장한다.
  3. 다음 영상/감시 콜백이 저장된 값을 읽는다.
  4. 현재 Basic_P의 값과 다르면 새 조향 객체를 만든다.
  5. _reset_processing()으로 이전 결과를 무효로 만든다.
worker가 사용하는 기존 객체는 직접 수정하지 않는다. 검출기는 유지한다. 같은 값이거나 다른 조향기를 사용 중이면 현재 객체를 교체하지 않는다.




공통 초기화가 하는 일


_generation += 1          # 이전 작업과 새 작업의 설정 번호를 구분
_pending_frame = None     # 아직 시작하지 않은 영상 비우기
_last_valid_frame_at = None
cmd_vel_pub.publish(Twist())  # 먼저 정지 명령 발행


_reset_processing()은 _job을 지우거나 worker를 강제로 취소하지 않는다. 예전 작업이 완료되면 job.generation != self._generation으로 판별해 버린다. 그 작업이 끝나 회수되기 전에는 새 작업도 시작되지 않는다.


두 선택 토픽은 독립적이고 검출·조향의 자료 의미를 자동 검사하지 않는다. 결과 형식까지 다른 쌍은 두 기본값을 함께 맞춰 재시작해 확인한다. 자료형·좌표·단위·미검출 의미는 팀 코드에서 일치시켜야 한다.

로컬 OpenCV 뷰어로 입력과 결과 보기
GUI 환경에서 패키지를 빌드하고 setup을 적용한 뒤 ros2 run driving driving_debug를 실행한다. 세 camera 토픽과 디버깅 JPEG를 별도 창으로 보여준다. 정상 영상이 도착한 창부터 열리며 각 영상의 시각을 동기화하지 않는다. 영상 창에서 q/Esc 또는 터미널의 Ctrl+C로 뷰어를 종료한다. namespace/remap 사용법은 기여 안내 8.5절을 참고한다.


정상 영상의 미검출과 손상된 입력은 다르다
basic에서 정상 영상의 미검출은 None이다. Basic_P는 이를 기존 극단값으로 바꾸어 전진·회전한다. 공통 노드가 None만 보고 정지시키지 않는다. 반면 디코딩 실패·지원하지 않는 해상도는 검출기가 예외로 알리고, 노드가 처리 실패로 0 Twist를 발행한다.


디버깅 실패가 조향에 미치는 영향
디버깅 생성 중 예외는 FrameResult.debug_error에 담는다. 유효한 Twist는 유지하고 해당 영상은 보내지 않는다. 다만 JPEG 생성도 같은 worker에서 끝내므로 오래 걸리면 전체 결과가 0.5초 제한을 넘길 수 있다.


시간 제한과 종료에서 기억할 점
  • 나이는 수신 시각 기준이다. 촬영 지연·전송 지연은 header로 검사하지 않는다.
  • steady clock으로 감시하지만, 콜백 지연과 실행 환경의 영향을 받아 하드 실시간을 보장하지 않는다.
  • destroy_node()는 입력/타이머 처리를 막고 ROS가 살아 있으면 0 Twist를 보낸 뒤 worker를 기다린다. 영구 정지한 계산을 강제로 종료하는 기능은 없다.
  • 입력이 끊겨도 디버깅 뷰어에 마지막 영상이 남을 수 있다.
